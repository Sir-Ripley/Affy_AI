## 2024-03-17 - Potential performance bottleneck in encodeBitmapToBase64Png
**Learning:** The `encodeBitmapToBase64Png` function uses `ByteArrayOutputStream`. Creating a new stream and calling `toByteArray()` creates an extra copy of the underlying array, which can be inefficient for large images. Using a stream that allows direct access to the buffer, or pre-sizing the stream could avoid this. Furthermore, `ByteArrayOutputStream().use { ... }` would be better to ensure the stream is closed, although for `ByteArrayOutputStream` closing is a no-op, it's good practice. A better approach might be to size the `ByteArrayOutputStream` based on the bitmap size to avoid reallocations.
**Action:** Consider optimizing `encodeBitmapToBase64Png`.
## 2024-03-17 - Unnecessary use of LinkedList
**Learning:** The `LinkedList` class is used to collect bitmaps and blobs in `sendMessageStream` inside `Chat.kt`. While this isn't a massive performance hit, `ArrayList` (or simply `mutableListOf()` in Kotlin) is generally preferred due to better cache locality and less overhead unless you frequently insert/remove from the middle of the list. Here we just add elements and then iterate over them, making `ArrayList` the superior choice.
**Action:** Replace `LinkedList` with `ArrayList` or `mutableListOf()`.
## 2024-03-17 - Inefficient `toTypedArray()` call in Chat.kt
**Learning:** In `Chat.kt`, the history list is converted to an array using `toTypedArray()` every time a message is sent. This creates a new array every time, copying all elements. If the history grows, this could be a slight performance hit. A better approach is to pass a List to `generateContent` or `generateContentStream` directly. However, the `GenerativeModel` API uses `vararg prompt: Content`. To avoid copying the whole array plus one element, a List based API or spreading `history + prompt` might be used, although `*history.toTypedArray(), prompt` still creates a copy. The most optimal way is to add `prompt` to a list and pass the entire list to `generateContent` that takes an `Iterable` or `List`. Since `generateContent` takes `vararg`, it might be necessary to just convert `history + prompt` to array. Wait, actually, let's see how `generateContent` is defined. It only has `vararg`. So an array must be passed. `(history + prompt).toTypedArray()` or `*(history + prompt).toTypedArray()` might be a little clearer, but performance-wise it still creates an array. So there might not be a huge optimization there without changing the API of GenerativeModel.

## 2024-05-13 - Cached enum values in FirstOrdinalSerializer
**Learning:** `FirstOrdinalSerializer` repeatedly invoked `enumClass.enumValues()` during deserialization and looped over all elements to find a matching serialName. Using `by lazy` cached collections reduces expensive reflection on each operation and prevents performance issues from constant iteration during massive serialization operations.
**Action:** Always cache Enum maps/values within custom serializers utilizing `by lazy` block to guarantee they are evaluated on the first access when enum instances are fully initialized.
